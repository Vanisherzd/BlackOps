# Knowledge-pack retrieval v2/v3: what the measurements show (2026-10-13)

Tables: `docs/kb-retrieval-eval.md` (regenerated by `scripts/kb-retrieval-eval.py run`, 3 s). Code:
`kb/src/blackout_ops_kb/retrieval_v2.py`, tests `kb/tests/test_retrieval_v2.py`. The v1 pack is unchanged; the agent
tool now reads v3 (section "The agent now uses v3"); `scripts/kb-eval.py` gained opt-in switches only (unset, it
runs v1 as before, now pinned explicitly). v2/v3 read the v1
SQLite and write `logs/kb-retrieval-eval/corpus_v2.jsonl` / `corpus_v3.jsonl`.

## Step 0: a measurement that does not need the model

`scripts/kb-eval.py` takes 50 minutes and cannot tell a retrieval failure from a model failure. The new evaluator
scores retrieval alone on two splits: dev (197 cases of the pack's dev split, inputs built by the same pipeline as
kb-eval's, used to choose thresholds) and eval (the 63 kb-eval cases at 8x, reported, never tuned on). It reproduces
the end-to-end finding without a model call: v1 with the model's one-line query says `matched` on 33 % of eval cases
(kb-eval measured 37 %) and is right on 1 of those 21.

## Step 1: what the quick fixes change

| | v1, model one-liner (as shipped) | v2 |
|---|---|---|
| eval: `matched` | 33 % (21 / 63) | 0 % |
| eval: correct matches | 1 | 0 |
| eval: false alarms on `other` cases | 17 / 54 | 0 / 54 |
| eval: label@5 (best query) | 14 % (symptom lines) | 19 % (symptom lines) |
| dev: label@5 (best query) | 7 % | 13 % |

1. **`matched` no longer lies.** v2 tokenises on word boundaries, drops generic incident words, weights by IDF and
   measures how much of a card's own symptom signature the incident shows. On dev no coverage bar yields more correct
   than wrong matches: at 0.10 the cards would match 60 cases, 1 correctly; at 0.25, 3 cases, 0 correctly. So the bar
   chosen on dev is "never", and v2 answers `insufficient` everywhere, which is what the agent tool already treats as
   "not a basis for repair". This removes the misleading cards that made the rag arm worse than no retrieval; it does
   not add knowledge.
2. **Case retrieval improves a little and still loses to a lookup table.** label@5 roughly doubles on dev (7 → 13 %)
   and rises on eval (14 → 19 %), but the most frequent train label of the source system alone scores label@1 11 %
   (dev) and 13 % (eval). With this corpus, retrieval does not know more than the label prior.
3. **The hard scenario filter is harmful** (dev label@5 13 → 7 % with it back on), as expected from a substring rule
   that confines any query mentioning "disk" to disk_full cases.
4. **Label-only cases must stay.** Down-weighting the 754 cases without evidence (half weight, or dropped) lowers
   dev label@5 from 13 % to 7 % and 6 %: they carry the answers and are reached through service names.
5. **Scenario relabelling (162 cases).** RCAEval `disk` and `io` are I/O stress, not a full disk; `pod kill` and
   `pod failure` are single kills, not restart loops. After correction the 63 eval cases contain **9** target-scenario
   cases, not 35, and dev 13 of 197. Every per-scenario figure in `docs/kb-eval.md` rests on the old labels.
6. **458 duplicate case texts merged** (1,644 → 1,186 cases), almost all RCAEval.

## Step 2: index each case by its own telemetry

The ceiling was the data: cards say "DiskPressure", "no space left on device"; a node-disk-fill incident's telemetry
says `node_disk_read_bytes_total` moved; 754 of 1,186 cases contained only the answer. So every train case was run
through the same pipeline as the evaluation inputs (raw telemetry -> `compress_events` at 8x -> `incident_query`) and
indexed by what its own incident showed (`scripts/kb-retrieval-eval.py prep-train`, 1,644 of 1,644, 12 min on 14
workers; `build-v3`). Train split only; dev and eval never enter the index. Runs of the same fault on the same
service are no longer merged (their telemetry differs), so v3 has 1,557 cases.

| | dev label@1 | dev label@5 | eval label@1 | eval label@5 |
|---|---|---|---|---|
| lookup table (most frequent labels of the source) | 11 % | 50 % | 13 % | 65 % |
| v1 (current), best query | 5 % | 7 % | 10 % | 14 % |
| v2 (step 1) | 7 % | 13 % | 8 % | 19 % |
| **v3: cases indexed by observed telemetry** | **35 %** | **61 %** | **44 %** | **63 %** |
| v3, observed + original text | 32 % | 54 % | 38 % | 65 % |
| v3, entity names stripped | 34 % | 61 % | 48 % | 65 % |

Only label@1 beats the lookup table. The five most frequent labels of the source system already contain the answer
50 % (dev) and 65 % (eval) of the time, and the model is given the full label list in its prompt anyway; v3's top 5
(61 %, 63 %) add nothing over that list. What v3 adds is the right label *first*.

The configuration for the model run was chosen on dev (observed index, entity names kept; the two are within a point
on dev). The query must be the telemetry extract: the model's one-line query on the v3 index gets 21 % label@1.

**Read this as recurrence, not diagnosis.** On eval, 24 of the 28 top-1 hits are a train incident with the same fault
on the same service (dev: 46 of 69): RCAEval and AIOps run each fault several times and the pack's split spreads
the runs. v3 is very good at "this happened before, here", which is what an incident memory on a real site is for,
and still weak on a fault it has not seen on that service (eval: 4 other hits in 63).

**Cards stay unmatched.** Matching a card by a vote of the nearest incidents (N of the top 5 share a target scenario)
was measured on dev: N = 2 or 3 gives 3 correct and 3 wrong matches, N = 4 or 5 none. No N clears more correct than
wrong, so the vote is off and v3 still answers `insufficient`; what it adds is the similar-case titles the agent tool
already prints (`similar historical cases: delay fault on adservice (Online Boutique)`).

## The model, end to end (`docs/kb-eval-v3.md`, 2026-10-13)

`KB_EVAL_OUT=logs/kb-eval-v3 KB_EVAL_TAG=-v3 KB_RETRIEVAL=v3 KB_QUERY=incident scripts/kb-eval.py run` then
`report`: the same 63 cases x 6 ratios x 2 arms as run 4, Nemotron thinking off, 756 calls in 30 minutes, no errors.
Only the retrieval changed (v3 index, query extracted from the telemetry instead of written by the model).

| strict accuracy | 1x | 2x | 4x | 8x | 16x | 32x |
|---|---|---|---|---|---|---|
| run 4: telemetry only | 22 % | 24 % | 16 % | 24 % | 22 % | 22 % |
| run 4: + v1 retrieval | 10 % | 8 % | 11 % | 13 % | 13 % | 22 % |
| today: telemetry only | 22 % | 19 % | 25 % | 24 % | 27 % | 25 % |
| **today: + v3 retrieval** | **35 %** | **32 %** | **33 %** | **35 %** | **33 %** | **33 %** |

Paired over the 378 (case, ratio) inputs: v1 retrieval turned 50 right answers wrong and 16 wrong answers right;
v3 turns 16 right answers wrong and 53 wrong answers right (sign test p ≈ 1e-5; the 378 pairs are 63 cases at six
ratios, not independent, so read it as "clearly", not as that number). The telemetry-only arm is not perfectly
repeatable at temperature 0: between run 4 and today it changed verdict on 44 of 378 inputs, so a few points between
two runs is noise; the retrieval effect is not.

Where it comes from, consistent with the retrieval measurement: RCAEval 40 → 59 % strict (recurring faults on the
same service), Cloud-OpsBench 13 → 18 %, AIOps 13 → 15 %, RCA100 0 → 0 %. Retrieval costs about 150 prompt tokens and
1 s per diagnosis; the one-line model summary v1 needed (2-10 s) is gone. With retrieval the working point is 8x
(35 %, 14.6k tokens); service naming is unchanged (25-32 %).

Two lines of the generated report are v1-era metrics and mislead here: "retrieval's scenario guess" is
`infer_scenario` on the query text, not anything v3 decides; and "a similar case carried the label in its title"
uses the 6-character rule, so RCAEval's short labels (`disk`, `cpu`, `delay`) never count, which is why that line
shows lower accuracy with a hit (the hits are the harder sources). Per-scenario rows use the old scenario labels.

## Faults never seen on that service (leave-out, 2026-10-13)

The recurrence reading needed a direct test. `retrieval_v2.sibling_ids` names, for a case, the train incidents with
the same fault on the same service (same source, a shared label, an overlapping service name; when a side names no
service, the shared label is enough). `KnowledgeBaseV2.excluding(ids)` hides them, per thread, while that case is
retrieved; 56 of the 63 eval cases have some (6.3 on average, up to 30).

Retrieval alone (`docs/kb-retrieval-eval.md`, row "UNSEEN"): label@1 44 → 11 % on eval and 35 → 11 % on dev, i.e.
the lookup table's level; label@5 41 % / 32 %, below the lookup table's 65 % / 50 %.

The model (`docs/kb-eval-v3-unseen.md`; rag arm only, the telemetry-only arm from the v3 run reused):

| strict, 378 inputs | correct | vs telemetry only |
|---|---|---|
| telemetry only | 90 | – |
| v3, the same fault on the same service visible | 127 | fixed 53, broke 16 |
| **v3, the same fault on the same service hidden** | **95** | **fixed 35, broke 30** |

By source (correct of 378 inputs per arm, none / visible / hidden): RCAEval 65 / 96 / 66, Cloud-OpsBench 12 / 16 / 15,
AIOps 13 / 15 / 14, RCA100 0 / 0 / 0.

So on a fault the pack has not seen on that service, v3 is neutral: it no longer misleads the model (v1 broke 50
and fixed 16 with everything visible), and it does not help. The whole measured gain is recognising a recurrence.
That is a real capability for an edge site (the second occurrence of a fault starts with its name) and it is the
honest scope of the claim. Diagnosing a new fault from similar-but-different incidents does not work with this
corpus; the next lever there is not retrieval but the agentic variant (let the model pull more telemetry), or
cards written in telemetry terms. (The rag row's latency and energy in that report are not comparable: its power
trace was appended to the v3 run's.)

## The agent now uses v3 (2026-10-13)

`scripts/agent.py` opens `kb/artifacts/corpus_v3.jsonl` (3.5 MB, copied from the build, now a tracked artifact) with
`retrieval_v2.AGENT_DEFAULTS`; `KB_RETRIEVAL=v1` restores the pack as shipped. Two things were added for the agent's
own queries, which are typed words rather than a telemetry extract, and the gate self-test
(`scripts/test-retrieval-gate.py`) is what caught the need:

- Typed errors still reach a card. With the card-side coverage of step 1, "write error: No space left on device"
  scored 0.19 and the disk card was lost (v1 matched it). Cards now match by symptom phrase: one of the card's own
  symptom phrases occurs whole in the query and the IDF of its words sums to at least 8. The bar is the lowest with
  no wrong match on dev (bar 6: 7 wrong, 4: 16 wrong; no bar gives a correct match on telemetry). Measured: "No space
  left on device" 16.3 -> disk card; "connection refused" 6.7 -> insufficient; "printer toner" -> nothing. On the
  telemetry queries of dev and eval it matches nothing, so the model-run results above stand unchanged.
- Typed words still reach cases. A pure telemetry index found no similar case for "No space left on device"; when
  fewer than k cases share a word with the query, the rest now come from the original case text. Telemetry queries
  always fill k, and the eval tables are identical with the fallback on.

Drills after the switch (`logs/drills-20261013-224553.log`, all nine cases once, through the NemoClaw sandbox):
9/9 autonomous, 0 fallback, 0 made worse, 0 false health claims, evidence-first and closure 100 %, median 49 s
(48 s on 2026-09-27). The agent called `search_incident_knowledge` 0 times, as in every drill before: the drills
show nothing regressed, and they do not exercise v3. A case whose fault is outside the runbooks is what would.

## A drill the runbooks do not cover: inode exhaustion (2026-10-13)

`faults.py inject inode-exhausted`: the front end's `/var/cache/nginx` is now a 16 MB tmpfs volume with 256 inodes
(`edge-cache`, held by a sidecar `edge-victim-cache` so a restart cannot clear it by accident); small files take every
inode while bytes stay free, the front end restarts and exits with `[emerg] mkdir() "/var/cache/nginx/client_temp"
failed (28: No space left on device)`. No runbook was written for it; the knowledge pack has an inode-exhaustion card.
New tools: `disk_usage` reports the scratch volume's space and inodes first; `clear_scratch_volume` empties it
(destructive, reviewer code key: the volume measured at 95 % or more).

Three drills with v3 (`logs/drills-20261013-231808.log`): 3/3 fixed, 2 autonomous (85-100 s: logs, `disk_usage`
shows inodes 100 %, clear, start) and 1 through `self_heal` (3.5 min). **`search_incident_knowledge` was called 0
times.** The v1 arm was not run: with no call, v1 and v3 are identical by construction.

Why the pack is never reached, measured: the skill says to ask it only when `search_runbooks` returns the catalogue,
and dense retrieval never returns the catalogue ("printer toner low" returns `disk-full.md`); `docker_logs` also
attaches the nearest runbook to any error line. Under the current skill the pack is unreachable, v1 or v3. And in this
case the decisive evidence came from the tool surface (an inode column), not from retrieval. To make the pack testable
in drills, the skill's trigger has to change (e.g. a runbook-relevance floor below which search returns the catalogue,
or "consult the pack when the attached runbook's steps do not match what you see"); that is a design decision, not
made here.

## The pack reaches the agent: cards ride along with runbooks (2026-10-14)

Two ways to make the pack reachable were measured before choosing. A runbook-relevance floor ("below it, no runbook
covers this, ask the pack") does not separate: covered symptoms score 0.66-0.88 against their runbook, uncovered ones
up to 0.73 (12 calibration and 12 test symptoms written before scoring), and the inode log line scores 0.75 against
`disk-full.md`. The pack's own confidence does: on the 24 uncovered symptoms its phrase rule pushed 6 cards, 5 right
(TLS x2, systemd, DNS x2; the wrong one, "permission denied" -> the invalid-command card, is adjacent), stayed silent
14 times correctly and missed 4; on 38 covered symptoms it added 3 cards, each consistent with the runbook.

So `agent.knowledge_note` appends the pack's card, labelled a hypothesis from other systems, wherever a runbook is
attached (`docker_logs`, `search_runbooks`), only when v3 says `matched` (nothing under `KB_RETRIEVAL=v1`, whose
`matched` was wrong 20 times in 21). The gate is unchanged: a card never counts as a runbook. The skill's step 4 says
what the card is and to test its CHECK lines when the runbook does not fit. On the inode case the card is
`solution-linux-disk-log-growth`, whose first check is `df -hT && df -i :: separate block exhaustion from inode
exhaustion`; the sandbox session transcripts show it in the agent's context.

Drills after the change (`logs/drills-20261014-012027.log`, `-014114.log`): the nine seen cases 9/9 autonomous, the
inode case 4/4 autonomous (median 92-108 s), no fallback, nothing made worse.

**An incident during those drills.** In one inode run the agent also called `cleanup_disk`, and the reviewer approved
it: the log said "No space left on device" and the Spark's `/` is genuinely at 94 %, above the 85 % precondition. It
deleted seven project logs, among them every earlier `logs/drills-*.log` (2026-09-27 to 2026-10-13); `logs/` is not
in git and no copy exists. What remains of those runs: `docs/scorecard.md`, the numbers quoted in this file and in
`docs/agent-design.md`, and the agent-side transcripts in the sandbox. Two fixes: `cleanup_disk` never touches
`logs/drills-*.log` (evidence, like `logs/agent/`), and the reviewer's code key refuses `cleanup_disk` when the full
filesystem measured in the incident is the scratch volume. Both are asserted in `scripts/test-retrieval-gate.py`.

## Does the card help? A/B on the inode case (2026-10-14)

To measure the card, the tools must not hand over the answer: with `OPS_INODES=on-request` (experiment only; the
default still shows inodes) `disk_usage` reports inode figures only when called with `inodes: true`, so whether the
agent thinks of inodes is part of what is measured. The two arms differ only in the card: A = v3 (the card on the
inode log line is `solution-linux-disk-log-growth`, first check `df -hT && df -i :: separate block exhaustion from
inode exhaustion`), B = `KB_RETRIEVAL=v1` (no card). Five runs each, alternating A/B, ops API restarted with each
arm's environment before every drill (`scripts/ab-drill.sh`; `logs/ab-20261014-015134-{A,B}.log`).

| | A: card | B: no card |
|---|---|---|
| autonomous | **4/5** | 1/5 (+1 via self_heal) |
| failed | 1 | 3 |
| first `disk_usage` asked for inodes | **3/5** | 1/5 |
| median seconds | **94** | 353 |
| `search_incident_knowledge` called | 0 | 0 |

The mechanism is the expected one: runs that asked for inodes before trying to clear the volume passed, and the card
made that first ask more frequent. The size is not established: 4/5 vs 1/5 autonomous is p = 0.21 (Fisher, two-sided).

A confound that amplified the difference, the same in both arms: when the agent tried `clear_scratch_volume` after a
space-only reading, the reviewer's code key refused with "scratch volume at space 0%, below 95 % — it is not what is
full", a conclusion the measurement did not support; four of the five runs that met it failed. It now says what was
measured ("its inode usage was not measured"), asserted in `scripts/test-retrieval-gate.py`. A rerun with the honest
message and more runs per arm is what would size the card's effect.

- The pack never opens the runbook gate; a fault no runbook covers still needs one consulted (or two refusals).
