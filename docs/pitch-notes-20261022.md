# Blackout Ops：完成度、特點、設計合理化（2026-10-22 11:00，給上台與 Q&A 用）

每一句都能回指到 repo 裡的數字或 commit；沒量過的就寫沒量過。數字出處：`docs/results-summary-20261022.md`。

## 1. 完成度（誠實分三級）

**做完、量過、可重跑**
- 事故全線：2 s 巡檢 → triage → 派工 sandbox agent → 唯讀診斷（23 個工具＋證據包）→ 白名單修復 → Guardrails rail → 兩把鑰匙審核 → 風險動作人工審批 → 每個動作後自動健康檢查 → 結案寫回事故記憶。
- 故障目錄 **45 案、八類**（容器生命週期／設定部署／網路 DNS／資源 OS 上限／資料內容／服務行為／安全／複合），每案有注入、驗紅、reset 回綠。
- 全目錄 regression（36 案，Spark）：自主修復 **30/32、越修越壞 0、謊報 0**；盲測四批 **17/18**；安全注入 **2/2** 擋下；Thor 基本配方 round 1 進行中（前 8 案 8/8）。
- 速度：偵測到派工 **4.0–4.9 s**，簡單故障 **15 s** 結案；Lightning 在 vLLM 上 **65–100 tok/s**（DSpark，Spark）；審核 15.3 s → **1.0–1.5 s**。
- 邊緣資源：整套 ≈ 45 GB；KV 預留可調；知識庫索引 2.5 GiB → **幾 MB**（FTS5）；磁碟 1.4 GB → 253 GB。
- 知識層：runbook 稠密檢索（每場都用）；修復卡 phrase gate 漏推 0/8 → 6/8、誤推 3 → 0；社群層 158,881 筆離線語料＋rerank＋判官閘門（離線評測：機房探針前 1 對題 45%、前 5 71%）。

**做了，但效益還沒證實（照實講）**
- 社群層推上關鍵路徑：A/B 推送開 7/10 對關 8/10，兩臂 made-worse 0；推送少、0 次被用上。閘門已修，Thor 上無 reranker 時判官把候選全退掉（寧缺勿濫）。
- 事故記憶推送（Thor round 2 量中）。
- adaptive 多代理：同成功率、2.4× 慢、多一次謊報 → 預設關。
- 訊號 watcher：偵測到、但兩個安靜故障 240 s 內沒結案 → 預設關。

**已知弱點與沒做的**
- `front-rlimit-nofile`（worker fd 上限）0/4：agent 一直改前端 default.conf、不重建。
- 幾個網路綁定類案例 5–8 分鐘才修好。
- Thor 數字只有基本配方（無 DSpark、reranker 剛抓）；Spark 數字多。
- 沒做：真資料庫容器、備援切換、tc/iptables 類網路故障（容器無 NET_ADMIN）。

## 2. 特點（每個配一句證據）

1. **證據先於動作、動作後必驗**：runbook gate 在工具層強制、每個改變狀態的工具自動附健康檢查、健康檢查看內容不只看 200 → 謊報 0、越修越壞 0。
2. **單一變更路徑、五道關**：白名單工具 → runbook gate → NeMo Guardrails → 兩把鑰匙（code key＋模型）→ 人工審批；破壞性工具永遠不給 agent → 注入指令 2/2 擋下、破壞性動作 0 次。
3. **知識由近到遠、用推的不用拉的**：事故記憶 → runbook → 修復卡 → 社群層（FTS5 → rerank → 判官）；全部由工具層附在證據後面。拉的歷史：70 場 1 次。
4. **寧缺勿濫的 RAG**：判官說不對題就不給；類別命中與真相關只有 34% 一致，所以我們不拿類別命中當品質。
5. **閉環學習不重訓**：結案驗證 200/200 才寫記憶；下次同症狀直接帶上「上次幾秒、做了什麼」。
6. **不是劇本**：45 案八類、盲測 split（寫完故障不改 agent）、dashboard「隨機真實故障」按鈕（agent 不知道抽到哪個）、全目錄 regression。
7. **可重跑的評分**：`regression.sh` ＋ `score.py` 多欄位（自主／兜底／越修越壞／謊報／證據先於動作／效率／cause named），不是一個通過率。
8. **邊緣最佳化有量有取捨**：DSpark +27–49% decode、k=2 保 prefix cache 31.9%、KV 0.25、記憶體治理、FTS5、審核不思考；MTP／Palu／多代理量過不採用。
9. **全離線、全在 repo**：模型、語料、sandbox 本地；demo 有斷網段；所有腳本、log、文件在 main。
10. **研究紀律**：判準先登記再跑、A/B、負結果照寫（`docs/kb-community-20261022.md`、`docs/optimizations-20261022.md`）。

## 3. 設計合理化（決策 → 替代方案 → 為什麼 → 證據）

| 決策 | 替代方案 | 為什麼這樣選 | 證據 |
|---|---|---|---|
| 小模型（30B-A3B，3B 活躍）＋工具層規則 | 更大模型／純 prompt | 離線 128 GB 機器要留餘裕；可靠性來自工具層不是模型大小；prompt 說「先查 runbook」模型不照做，工具層強制後才每場都查 | Nano 時代盲測 6/15 → Lightning＋工具層 17/18；decode 14 s／事故是瓶頸不是 prompt |
| 單一變更路徑 | agent 直接 shell | 安全可證明：五道關都在程式裡，不靠模型自律 | 注入 2/2 擋下、破壞性 0 |
| 兩把鑰匙審核 | 純模型審核 | 純模型在同一份證據上翻盤；code 先算充分條件，模型只判相關與矛盾且必須引用一行 | 3/3 一致 |

## 4. Q&A 預演（刁鑽題）

- **五張牌是不是劇本？** 五張牌是 demo 守門；證據是全目錄 regression、盲測 split、隨機真實故障按鈕。
- **RAG 到底有沒有用？** runbook 檢索每場都用、命中 23/23；社群層目前「無害、未證實有益」，而且我們量得出來；事故記憶層正在量。不會說它有用。
- **為什麼不用更大的模型？** 離線、單機、要留餘裕給 sandbox 與知識層；可靠性靠工具層與審核，不靠模型；30B-A3B 已經 65–100 tok/s。
- **會不會越修越壞？** 0 場；每個動作後自動健康檢查、known-good 快照、reviewer 兩把鑰匙、風險動作人工審批。
- **安全？** agent 永遠拿不到破壞性工具；log／設定檔注入 2/2 擋下。
- **換一台機器會不會壞？** Thor 今天早上從頭拉 repo、重建 sandbox、preflight 全綠、round 1 前 8 案 8/8。
- **最難的案例？** fd 上限 0/4、網路綁定類 5–8 分鐘；都在表裡。
